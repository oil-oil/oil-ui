# Style comparison page

Put several candidates on one page side by side for the user to choose from. The user can view them side by side or one at a time, switch between desktop and mobile, look at actual size, and select and copy a direction. The shell of the comparison page only compares and selects. It carries no style bias of its own and is not a reference for the candidates.

Keep the core content, the primary action, and the target users the same first, then vary composition, information organization, typographic character, color relationships, density, and image language. The number of candidates follows the request and the real differences. Do not copy the whole product to pad out proposals, and do not apply the shell's style to the candidates.

The comparison page is a visual exploration tool. HTML previews run no scripts and submit nothing by default, except candidates marked interactive and local URL candidates (see "Preparing the input"). Interaction acceptance that needs real data, login, or a backend still happens in the project.

## Preparing the input

Style cards use this comparison page too: one round holds 4–6 cards, and `round` says "Style cards". After the user picks a style, open the next round for layout proposals. How to make cards is in "Style cards" in [Design direction](design-direction.md).

Generate one comparison page per round. When a candidate can run, use the real page: embed separately written HTML previews directly, and use local URLs for proposals inside a project. Use screenshots only when no runnable page can be obtained. One screen per proposal: for existing projects choose the entry point or the step that differs most, and for whole-site proposals include only the representative page and describe the other pages in the notes. Produce a mobile version separately only when mobile is the main device. Do not hand-write a summary page.

Place `manifest.json` and the candidate files in the task directory. HTML candidates are documents with a `head` and CSS written inside the page. Images, fonts, and video are referenced by relative paths to files in the task directory, for example `img/hero.jpg`, and the generator inlines them into the comparison page. Do not convert images to base64 inside the candidates yourself. The files become large and hard to edit. Do not reference network resources or files outside the task directory, and only use in-page anchors as links. You may keep code so the candidate can be opened on its own, but the comparison page does not run its scripts.

Candidates must show their design content even when scripts do not run. For pages whose interface is generated by scripts, obtain static HTML or a real screenshot first. Do not hand an app entry point with only an empty mount node to the comparison page.

Candidates must not use nested documents such as iframe, object, or embed. Convert the needed content into a static page or a screenshot first. Saved copies of existing pages often carry `srcset` or `<picture><source>` responsive images, and the generator rejects them: change them to a single `<img>` referenced by relative path, or use a screenshot as an image candidate.

Image candidates support PNG, JPEG, and WebP. Look at the image and record which page and state it represents, so that images from different tasks or different states are not compared for style. Source files must be in the manifest's directory or a subdirectory of it.

The manifest uses fixed fields, structured as follows. Text in angle brackets is a placeholder description. Replace all of it with the real content of this round's direction cards. Do not keep placeholder text as a style:

```json
{
  "schemaVersion": 1,
  "lang": "<zh or en>",
  "project": "<project name>",
  "brief": "<the content and main task all candidates share>",
  "round": "<round, for example 01>",
  "candidates": [
    {
      "id": "<unique lowercase identifier>",
      "name": "<direction name>",
      "concept": "<north star: one sentence of experience intent that can guide trade-offs>",
      "typography": "<the actual type families, weights, and scale relationships>",
      "palette": ["<hex color>", "<hex color>", "<hex color>"],
      "traits": ["<observable trait>", "<observable trait>"],
      "kind": "html",
      "source": "<relative path to the candidate file>"
    }
  ]
}
```

Fill `lang` from the conversation language: `"zh"` for Chinese conversations, `"en"` otherwise. It only sets the language of the comparison page's shell and does not affect candidate content. When omitted, the browser language decides: Chinese browsers get Chinese, everything else gets English.

For runnable previews you wrote yourself (a single HTML file with inline scripts), add `"interactive": true` to the candidate in the manifest. It can then be operated directly in single view, while the comparison page remains a single file that can be moved offline and needs no server. The card's bottom-left corner is labeled "Interactive". Such candidates can only run inline scripts. They cannot reach the network or load external files. Browser storage is replaced by an in-memory version that clears when the page closes. System dialogs such as `alert` and `confirm` do not appear, so use an in-page dialog when confirmation is needed.

For an app in an existing repository that has to run (for example a React or Vue project), set `kind` to `url` and replace `source` with a `url` field pointing at a page on the local dev server, for example `http://localhost:5173/orders?variant=b`. Such candidates run live inside the comparison page. Scripts and forms work as usual, and the app really reflows when the viewport switches to mobile. The card's bottom-left corner is labeled "Live". The address may only be localhost, 127.0.0.1, or ::1. When the page is blank, confirm the dev server is running and does not forbid embedding through response headers. These candidates depend on the dev server to be seen, so:

- Write the start command at the top level of the manifest, the same command you just used yourself: `"serve": {"command": "pnpm dev", "cwd": "<absolute path of the project>", "url": "http://localhost:3456"}`.
- On delivery, leave the dev server running, so the user sees the real page when opening the comparison page.
- When the service is not running, the comparison page tells the user to say "open the comparison page" in the conversation and shows this command.

Do not save a screenshot version by default. When the user wants a long-term record or wants to send it to someone, take a separate screenshot with the screenshot tool in [Tools](tools.md).

Add `"baseline": true` to the current version. It is placed first, its number shows as "Current", and the other directions are numbered from 01. At most one baseline per round. When changing an existing page, always include the current version so every direction is compared against it.

`id` uses unique lowercase letters, digits, hyphens, or underscores. `typography` describes the text relationships actually used, `palette` uses hex colors, and `traits` briefly states observable differences. Image candidates set `kind` to `image` and point `source` at the image.

## Generating and opening

Confirm Python is at least 3.10, resolve the script and the input and output arguments to absolute paths, and run the [generator](../scripts/build_explorer.py):

```text
<python> <skill>/scripts/build_explorer.py <task directory>/manifest.json --output <task directory>/style-explorer.html
```

macOS and Linux usually use `python3`, Windows usually uses `py -3`. Confirm the actual interpreter before running. Without the ability to run the generator, keep the input and candidates for direct viewing, say the comparison page has not been assembled, and do not improvise another tool.

Overwriting is refused by default. When you really need to update this round's existing comparison page, add `--force` explicitly or use a new output filename. On input errors the old output is kept. The generator does not overwrite source candidates, and it does not allow writing its output into the skill directory.

Open the returned local HTML in a browser. HTML previews and screenshots are already inlined, so the single file can be viewed wherever it is moved. Local URL candidates need the dev server running. The template file itself has only an empty state. It is not the user's final comparison page. After the skill is updated, already generated HTML does not change on its own. Regenerate from the original manifest with `--force` when needed.

When the user later says "open the comparison page": read `serve` from the manifest next to the comparison page, run `command` in the background inside `cwd`, wait until `url` is reachable, then open the comparison page in a browser. When the port is taken, first confirm whether the process holding it is the same project.

## Viewing and recording the choice

HTML candidates are shown in the same logical viewport by default: desktop 1280×900, mobile 390×844. Cards are scaled proportionally so they fit on one screen. To judge text size and detail, enter single view and use "Actual size (100%)" to check the real typesetting. "Fit to window" may still shrink it, so it cannot be used to claim readability passes. After switching to the mobile viewport, confirm a real reflow rather than a shrunken desktop.

Clicking "Select" copies a short sentence, for example "<round>: Go with 03 <direction name>". When the user pastes the copied result or states the choice directly, the agent matches the round and number against the current manifest, confirms it belongs to this round, then updates the choice and the user's remarks in the design notes in the task directory and moves on: a chosen style card leads to layout proposals, and only a chosen layout proposal leads to the full page, see step 1 of SKILL.md. For comparison pages made for other purposes, return to the flow that generated them. The browser's local storage writes back to no file and sends no message to the agent on its own.

## Checking the actual result

Verify the candidates: every screen matches the page, state, and viewport written in the manifest, and the fonts of the product's language really rendered. The comparison page's own side-by-side view, single view, copying, and offline opening are covered by the skill's bundled regression tests. Do not verify them in the task, do not read the template source, and do not clear any storage in the user's own browser.
